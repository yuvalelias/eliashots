# פרומפט: מהירות וביצועים ל-eliashots.com

היי קלוד. אני יובל אליאס. אני רוצה שתשפר את המהירות והביצועים של eliashots.com. אתה עובד לבד ומוביל את זה מההתחלה ועד הסוף: מודד, מתקן, מודד שוב ומדווח. יובל מחליט, קלוד מממש.

## המטרה
- **היעד:** Core Web Vitals ירוקים בנייד בעמודים החשובים: LCP מתחת ל-2.5 שניות, INP מתחת ל-200ms, CLS מתחת ל-0.1. ציון Lighthouse נייד גבוה ככל שאפשר, בלי לשבור כלום.
- **העמודים החשובים, לפי הסדר:**
  1. דף הבית.
  2. /the-full-process/ (עמוד המכירה, עם #prices).
  3. /ההצעה-של-המאסטרקלאס/ ו-/טעימה-חינמית-מהאקדמיה/.
  4. /lets-make-a-connection/.
  5. העגלה וה-checkout.
  6. שיעור ב-LearnDash, כמשתמש מחובר.

## מה כבר ידוע (נבדק ב-21.10.2026, בקריאה בלבד)
- **אחסון:** WordPress.com Atomic, עם Batcache וה-CDN של WordPress.com. דף הבית הגיע מהמטמון (HIT). משתמשים מחוברים לא מקבלים מטמון.
- **אתר staging:** https://staging-b482-eliashots.wpcomstaging.com.
- **גישה:** קונקטור WordPress.com (כלי MCP) על שני האתרים: תוספים, הגדרות ותוכן.
- **ה-HTML של דף הבית שוקל 561KB.** בערך 283KB מתוכם הם CSS שמוטמע בתוך הדף (`wpr-usedcss`), מהפיצ'ר Remove Unused CSS של WP Rocket. זה החשוד הראשון.
- **כפילויות אפשריות:**
  - מטמון ואופטימיזציה: WP Rocket, לצד Batcache, ה-CDN ו-Jetpack Boost (ה-API שלו פעיל).
  - שלוש ספריות בלוקים: Spectra Legacy, Kadence Blocks ותוסף Gutenberg (תוסף פיתוח).
- **צד שלישי:**
  - GTM, Clarity, Facebook, Site Kit וסטטיסטיקות Jetpack.
  - Complianz, הנגישות של Wemake, וידג'ט ביקורות Google של Trustindex, Strong Testimonials ו-Presto Player.
  - שלושה סרטוני YouTube מוטמעים בדף הבית.
- **תמונות:** 32 בדף הבית, 29 מהן עם lazy. `fetchpriority="high"` מופיע 5 פעמים, וצריך אותו רק על תמונת ה-LCP.
- **תנועה נמוכה:** כ-800 צפיות בחודש, אז כנראה אין נתוני CrUX מהשטח. עובדים עם מדידות מעבדה.
- **PageSpeed API בלי מפתח נחסם (מכסה):**
  - מריצים Lighthouse מקומית: `npx lighthouse@12`.
  - בסביבת הענן של Claude Code הכרום נמצא ב-`/opt/pw-browsers/chromium` (להגדיר `CHROME_PATH`).

## מה אסור לשבור
- **מעקב:**
  - GTM, Clarity ופיקסל/CAPI של Meta (דרך ה-CRM).
  - Smoove וה-UTM בטפסים.
  - אחרי כל שינוי ב-JS, ובמיוחד Delay JS, מוודאים שהאירועים עדיין יוצאים.
- **חוק:** Complianz (הסכמה לעוגיות) ו-Wemake (נגישות) נשארים ועובדים.
- **כסף וגישה:** ה-checkout של CardCom, ההרשאות ב-LearnDash, מערכת האימונים וה-CRM (/crm).
- **מראה:** שום שינוי ויזואלי. משווים צילומי מסך לפני ואחרי, בנייד ובמחשב.

## שיטת העבודה
1. **מדידת בסיס:**
   - 5 ריצות Lighthouse נייד לכל עמוד, ולוקחים את החציון. שומרים JSON וצילומי מסך.
   - מודדים גם את ה-staging, כדי לוודא שהוא מייצג.
2. **אבחון:** מה תוקע את ה-LCP, איזה CSS ו-JS חוסמים, כמה שוקל כל תוסף וכל סקריפט חיצוני, ומה כפול.
3. **תוכנית:** רשימת תיקונים מסודרת לפי השפעה צפויה מול סיכון, ב-`perf-plan.md`.
4. **לולאה ב-staging:**
   - שינוי אחד בכל פעם, מדידה ובדיקה שלא נשבר כלום.
   - משפר: נשאר. לא משפר או שובר: חוזרים אחורה.
   - הכל נרשם ב-`perf-log.md`.
5. **חבילה לאתר החי:**
   - רשימה אחת של השינויים המוכחים, עם המספרים לפני ואחרי ודרך חזרה לכל שינוי.
   - מעלים רק באישור שלי, ואחרי ההעלאה מודדים שוב באתר החי.
